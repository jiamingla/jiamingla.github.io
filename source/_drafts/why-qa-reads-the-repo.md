一位主管問我：為什麼 QA 要去看 repo？

他問得沒有惡意，是真的困惑。而且他的困惑很合理——如果 QA 的工作是驗證功能有沒有照規格做出來，那看規格就好，看程式碼是 RD 的事。

我當下的回答是：因為這幾個產品沒有留下足夠的文件。

那個答案是對的，但它太弱了。它聽起來像在抱怨，而且它暗示「如果文件齊全，我就不用看了」。

後來我想清楚，那句話只對了一半。

---

## 先講那一半：沒有文件的時候，程式碼是唯一的現狀來源

我手上有幾個 Web 產品要測。它們的開發沒有走原本那套完整的流程，所以也沒有留下多少規格。

在這種情況下，我要回答「這一版到底做出了什麼」，只剩兩條路。

一條是去問人。但那要花掉別人的時間，而且我問到的會是「他記得的版本」，不一定是「現在跑的版本」。

另一條是去讀原始碼。

程式碼有一個別的東西都沒有的性質：**它不會過期。** 規格會跟現實脫鉤、口頭說明會記錯、上一版的測試紀錄會失效，但正在跑的那份程式碼就是現狀本身。

所以當我要盤點「哪些功能已經實作、哪些還沒」，讀 repo 是最快也最準的做法。

這一半成立。但它只處理了「現在怎麼動」。

---

## 另一半：正確的樣子，程式碼答不出來

一位敏捷教練講過一句話，我覺得是這件事最準確的版本：

> 看 code 的目的，只是知道現存系統怎麼動。至於正確的功能該長什麼樣，必須要有自己的想法。

這句話把事情切成兩半，而那兩半是測試成立的兩個必要條件。

**現狀**：這個按鈕按下去會發生什麼。這個可以從程式碼讀出來。

**預期**：這個按鈕按下去「應該」發生什麼。這個讀不出來。

如果我只做前半，我會寫出一種很危險的測試案例——它完全照著實作寫，所以永遠會通過。程式碼怎麼跑，我就怎麼驗。這種測試不驗證任何東西，它只是把實作抄了一遍。

測試要成立，得有一個獨立於實作的判準。那個判準在軟體測試裡有個名字叫 oracle，而 oracle 的來源只有三種：規格、領域知識、以及對使用者會期待什麼的判斷。

**沒有一種來自程式碼。**

---

## 所以讀 code 的正確用法是什麼

我現在是這樣用的：

**讀程式碼，是為了讓我問出對的問題。**

舉個實際的例子。我在 repo 裡看到某個欄位的值在特定條件下會走一條不同的分支。這件事規格裡沒寫。

這時候我不會直接把那個分支寫成測試案例——那就變成抄實作了。

我會去問：這個分支是刻意設計的嗎？使用者在什麼情況下會碰到它？碰到的時候應該看到什麼？

答案有三種可能。

**這是刻意的，只是沒寫進規格。** 那我拿到了一個新的測試情境，而且順便補了一個文件缺口。

**這不是刻意的，是 RD 當時為了繞過某個問題加的。** 那它可能是一個潛在的 bug，或至少是一筆該被記下來的技術債。

**沒有人說得出來。** 那這件事本身就是最重要的發現——有一段邏輯在產品裡跑，而沒有人知道它為什麼在那裡。

三種答案都有價值。而要問出這個問題，我得先看過程式碼。

---

## 回到那位主管的困惑

他覺得我在做不必要的事，是因為在他的模型裡，QA 的輸入是規格、輸出是測試結果，中間是一條直線。

那個模型在文件完整的時候成立。

但我手上這幾個產品不是那樣。輸入那一端缺了一塊，所以我得自己去把現狀拼出來，才有東西可以跟我的判斷做對照。

我沒有在做 RD 的工作。我在補一個本來應該由文件提供、但現在沒有的輸入。

這也是為什麼我同時在推另一件事：**讓規格補齊，比讓 QA 一直讀 code 划算。** 我讀 repo 是現在可行的辦法，不是長期該長的樣子。

---

> **帶走的一樣東西**
>
> 如果你也在讀程式碼來準備測試，記得把這兩個問題分開：
>
> **它現在怎麼動？** ← 這個去讀 code
>
> **它應該怎麼動？** ← 這個問人、查規格、或者用你自己對使用者的判斷
>
> 只做第一個，你寫出來的測試會永遠通過，而且什麼都驗不到。
>
> 而當你發現程式碼裡有一段規格沒寫的邏輯，先別急著測它。先問一句「這是刻意的嗎」——那句話常常比測試本身更有價值。
